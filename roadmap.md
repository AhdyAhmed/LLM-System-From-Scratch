# 120-day roadmap: a Java/Python chat platform with a transformer built from scratch

Read [design.md](design.md) alongside this plan. This roadmap allocates **120 workdays at 3–4 hours per day: 360–480 hours total**, including twelve integration/buffer days. Days are sequential workdays, not calendar dates. It targets a demonstrable headless portfolio system: authenticated chat APIs, streamed responses, a scratch transformer, Redis sessions/rate limits/cache, Kafka workflows, MLflow experiment tracking/model registry, Airflow batch pipelines, document retrieval, evaluation, and measured scaling behavior. Redis, Kafka, MLflow, and Airflow are required deliverables; there is no custom browser frontend.

The goal is a small, understandable system with evidence for its behavior. It is not a plan to reproduce the capability, training scale, or operating scale of a frontier assistant in four months. A tiny model can demonstrate the full training and serving pipeline while producing weak responses; report those results honestly.

## Starting assumptions and prerequisites

- You can already write basic Java and Python, use Git, understand HTTP and SQL, and work through algebra, derivatives, vectors, and matrix multiplication. Days dedicated to mathematics focus on transformer implementation. If these foundations are new, add preparatory weeks before starting rather than removing correctness or recovery work from this schedule.
- You have 3–4 focused hours on each workday. Long training jobs may run between sessions within a written compute budget; that does not count as additional hands-on development time. Do not leave an unmeasured laptop training job running indefinitely.
- The reference implementation is a Spring MVC modular monolith, a Java dispatcher worker, PostgreSQL, Redis, Kafka, and a Python FastAPI model process. Use Java 21, Maven, a stable compatible Spring Boot release pinned during setup, Spring Data JPA/Hibernate, Flyway, Spring Security, Spring Session/Data Redis, and Spring for Apache Kafka. Deliver a Postman collection, `curl.exe` examples, and a Python `httpx` SSE client; no Thymeleaf, HTML/CSS/JavaScript application, or frontend framework is in scope.
- PostgreSQL owns users, conversations, quotas, run state, durable events, outbox/inbox records, and leased work. Redis supplies shared sessions, atomic rate limits, and bounded cache-aside model metadata. Kafka transports versioned background events with at-least-once delivery; PostgreSQL leases execute long jobs outside Kafka poll loops. Add `pgvector` during retrieval. Kubernetes, distributed training, and paid model APIs remain optional.
- Use native Windows Java/Python training and serving with a **required Docker Compose CPU-infrastructure profile** for PostgreSQL, Redis, one Kafka KRaft broker, MLflow, and Airflow with LocalExecutor. Run Airflow on Linux containers/WSL2, with separate application/MLflow/Airflow PostgreSQL databases and credentials. Stage services by phase and budget disk before images; one local Kafka broker is not high availability. Do not assume container CUDA supports the old GPU. Airflow submits bounded jobs to an authenticated native GPU worker; it never runs arbitrary shell commands on the host.
- Start with FP32, a byte tokenizer, and a transformer of at most roughly one million parameters. The main local training target is roughly three million parameters using your own small byte-level BPE tokenizer. A roughly seven-million-parameter experiment is optional and requires profiling headroom. Use the exact configurations and limits in the design.
- Model code starts from random weights and implements the causal attention, normalization, residual blocks, learned positional embeddings, GELU feed-forward network, tied token/output embeddings, loss alignment, sampling, and cache behavior. PyTorch tensor operations, autograd, and optimizers are allowed; `nn.Transformer`, `nn.MultiheadAttention`, and pretrained language-model classes are not substitutes for these components.

## How to use each day

Spend about 20–30 minutes reviewing the relevant concept and previous evidence, two hours implementing the day's change, 40–60 minutes testing or measuring it, and 10–20 minutes updating notes and committing a coherent result. Each row describes one day's main outcome. Stop expanding its scope when the acceptance evidence exists.

Every tenth day is an integration/buffer day. Use it to close failures from that phase, reproduce the milestone, and capture evidence; it is not an invitation to add new features. A failed gate consumes buffer time or extends the calendar. Do not silently skip it to preserve the nominal day count. If a task exceeds its allocation, simplify dataset size, model size, document formats, and deployment extras first. Keep a minimal working slice of all four required infrastructure components. Adding them uses the former frontend allocation and tighter integration milestones; this remains an ambitious learning schedule.

All paths shown in backticks below are **planned repository artifacts**, not files claimed to exist today. Names are suggested and may be adapted consistently. `design.md` and this document are the planning deliverables. Do not commit secrets, private uploads, raw personal chat logs, bulk datasets, environments, or unbounded model binaries.

## Scope controls and evidence standards

- **Training budget:** choose token and wall-time limits from a representative pilot. Treat roughly 3M parameters as the intended local target, not a memory/performance guarantee. Record any smaller fallback. The optional roughly 7M tier must fit without compromising completion of the application and operations work.
- **Training/evaluation honesty:** distinguish training, validation, and held-out test data. Report tokenization details for perplexity; do not compare perplexities across different tokenizers as if they were directly equivalent. Show failed prompts as well as attractive examples.
- **Scalability evidence:** demonstrate replicas, bounded admission, durable state, failure recovery, and a reproducible load protocol. A fake provider measures application orchestration; a single older GPU measures only the documented local inference workload. Neither establishes internet-scale capacity.
- **RAG evidence:** measure retrieval against labeled questions and render verifiable sources. A pretrained CPU embedding model is a declared external dependency; the generative transformer remains your own random-initialized implementation. Retrieval success does not guarantee grounded answers from a tiny generator.
- **Infrastructure completion:** Redis, Kafka, MLflow, and Airflow must each have implementation, automated integration/failure evidence, operational instructions, and a recorded demo before release. A named dependency in Compose is not a completed integration. Keep all services private in the local profile; stage offline/online profiles to control memory/disk use.
- **Portfolio substance:** prioritize understandable code, tests for important invariants, diagrams matching the implementation, reproducible experiments, and working CLI/API demonstrations. Product-specific MLflow/Airflow consoles may show experiment/DAG evidence; a custom frontend is outside this project.
- **Data source:** [the TinyStories dataset card](https://huggingface.co/datasets/roneneldan/TinyStories) identifies the candidate dataset and currently lists `cdla-sharing-1.0`. Review the pinned source's terms and provenance before selecting a bounded subset; record attribution and redistribution decisions in the project. Self-authored material is suitable for the narrow SFT and document-retrieval fixtures.

## Optional work after the 120-day release

These are separate experiments, not hidden prerequisites or replacements for unfinished core work:

- Add RoPE, RMSNorm, SwiGLU, alternative position handling, or attention optimizations one at a time with correctness and cost comparisons.
- Investigate a larger scratch model, better data, DDP, mixed precision, or rented/newer hardware only after measuring the existing pipeline and setting a new budget. The current GPU does not establish compatibility with those paths.
- Explore preference data, DPO, and richer instruction tuning only after a meaningful supervised baseline and evaluation set exist.
- Add an explicitly separate pretrained generation provider to compare product quality with the educational scratch model; keep names, lineage, evaluations, and default demos unambiguous.
- Add richer document formats, reranking, vector indexes, external object storage, or tool use when concrete requirements justify them.
- Explore managed databases, cloud deployment, Kubernetes, highly available Redis/Kafka deployments, or additional worker/model replicas after identifying the bottleneck and operational need they address. Basic Redis/Kafka integration is already required in this roadmap.

Do not postpone the portfolio release until optional model quality or infrastructure work is complete.
